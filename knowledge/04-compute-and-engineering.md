# Compute Requirements and Engineering Architecture for Self-Play Training

Target hardware: RTX 3090 (24GB) + RTX 3060 (12GB), Ryzen 9 3900X (12C/24T), 128GB RAM, ~290GB free disk, Windows 11, no C/C++ compiler, PyTorch CUDA 12.6, Numba available. Game: Ultimate Tic-Tac-Toe (UTTT) — 81 cells, ≤81 plies/game, branching mostly ≤9, policy head size 81, input a handful of 9×9 planes.

## 1. Reference points: compute for small-game AlphaZero reproductions

The single most load-bearing reference is the **[Pgx paper](https://arxiv.org/abs/2303.17503)** (Koyamada et al., NeurIPS 2023), because its Gumbel-AlphaZero baseline uses a 6-block ResNet on boards the same size as UTTT's 9×9 grid, with published GPU-hours per game. The second most useful is Andy Jones' **["Scaling Scaling Laws with Board Games"](https://arxiv.org/abs/2104.03113)** (the `boardlaw` project), because it is the only source that reports a compute-vs-strength *frontier* rather than a single anecdote, and it targets Hex, a connection game structurally closer to UTTT than Go or chess.

## 2. Where the time goes: the self-play bottleneck

The Pgx paper states this explicitly for its Go 9×9 run: *"the time spent on self-play was dominant (more than 90%) compared to the time spent on training."* This holds across essentially every reference above — training a network this small (a few hundred KFLOPs–100 MFLOPs per forward pass) is cheap; generating tree-searched self-play data is the entire budget.

**Architecture A — CPU tree search + batched GPU inference server** (Leela-Zero/KataGo style). Each of many CPU threads/processes owns one game and walks its own MCTS tree in Python or C++, sending leaf-evaluation requests to a shared batching queue that a GPU inference server drains. This needs: fast per-game logic (ideally compiled, not pure Python), many CPU threads to keep the batch queue full, and careful queue/latency tuning. On a 12-core/24-thread 3900X, realistic parallelism tops out around 24–48 concurrent Python game-threads before GIL and interpreter overhead dominate — pure-Python MCTS here is the classic bottleneck (this is the reason C++ engines like Leela/KataGo exist at all). Numba-JIT-compiled game logic under Architecture C mitigates this without a compiler toolchain.

**Architecture B — fully vectorized self-play** (pgx+mctx/JAX style, or an equivalent batched-tensor MCTS in PyTorch). All N games (and, in the extreme "tensorized" version, all in-flight MCTS nodes) live as tensors on the GPU; one step advances every game and every tree simultaneously via batched ops (`vmap`/broadcasted indexing), so there is no CPU-GPU round trip per leaf. This is what let `boardlaw` run 32,000 Hex boards in parallel on a *single* RTX 2080 Ti, and what lets Pgx report ~10⁵ raw environment-steps/sec on a single A100 even for its slowest environment. In PyTorch this means representing the UTTT board, legal-move mask, and MCTS statistics (N, W, Q, P) as fixed-shape tensors indexed by a batch dimension, and expanding/backing-up the tree with gather/scatter ops instead of Python objects and pointers — this is exactly the approach ARENA's course teaches for Connect Four, "training to a strong level in under five minutes on a GPU."

**Architecture C — Numba-JIT game logic + batched inference server.** A middle ground: keep Architecture A's process-per-game model (simpler to write, no need to reinvent MCTS as a tensor algorithm) but JIT-compile the UTTT rules/legal-move generation with `@numba.njit` so each simulation step costs microseconds instead of Python-object overhead, and batch NN calls across all active games' pending leaves. This is the most PyTorch/Windows-friendly option given no C/C++ compiler is installed.

**Throughput estimates for a 6-block × 64-filter net (9×9 input), RTX 3090.** Anchoring on Pgx's Go 9×9 numbers (6×128 ResNet, 32 sims/move, batch 1024, single A100, 8.6 hours for 400 iterations × 256 steps × 1024 envs ≈ 1.05×10⁸ recorded positions): that is ≈3,400 recorded self-play positions/sec, and since each recorded position needed 32 network evaluations, ≈1.1×10⁵ raw NN forward evaluations/sec on the A100. A 6×64 net has roughly ¼ the convolution FLOPs of the 6×128 net (halving channels halves both fan-in and fan-out), so — if still compute-bound rather than launch-overhead-bound at large batch — raw NN throughput should scale up by roughly 2–4× (less than the ideal 4× because BatchNorm/activation/kernel-launch costs don't shrink with channel count). Net estimate for architecture B on a 3090 (weaker memory bandwidth than an A100 but comparable FP16/TF32 raw FLOPs): **~150,000–400,000 raw NN evaluations/sec**, consistent with the order of magnitude this document was asked to assume. A naive Architecture-A PyTorch implementation with Python-threaded MCTS will be well under this — likely one to two orders of magnitude lower — because GIL contention and per-leaf CPU-GPU dispatch dominate; this is precisely why Leela-Zero-class projects are written in C++.

**Known Ampere batched-inference behavior.** [CUDA-graph capture](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/) gives its largest wins exactly in this regime — small batches, many small kernels (conv+BN+ReLU repeated per residual block) — by eliminating per-launch CPU dispatch overhead; reported speedups against eager PyTorch range from roughly 1.8× to over 10× depending on model shape. Batch-size scaling for small CNNs on Ampere/T4-class GPUs is famously sub-linear-in-latency-but-super-linear-in-throughput (e.g., ResNet-18 goes from ~6ms at batch 1 to ~400ms at batch 512 on a T4 — roughly flat per-image cost once batch is large enough to saturate the SMs); no controlled batch-1-vs-256-vs-2048 benchmark specifically for a 6×64 9×9 ResNet on a 3090 was found, so the guidance above is an extrapolation, not a direct measurement, and should be validated with a short local microbenchmark before committing a training plan to it.

**Windows-specific PyTorch notes**:
- **`torch.compile` on Windows**: still not officially supported — the GPU path requires Triton, which historically had no Windows build ([pytorch/pytorch#122094](https://github.com/pytorch/pytorch/issues/122094), open since March 2024). Community forks ([triton-windows](https://github.com/woct0rdho/triton-windows)) now bundle TinyCC so `triton.jit` kernels work without installing MSVC, and recent releases target `torch.compile` compatibility, but this remains an unofficial, self-maintained path, not the default `pip install torch` experience.
- **CUDA graphs** are the more reliable Windows-native alternative to `torch.compile` for cutting per-step Python/launch overhead in the tight self-play inference loop, and require no compiler.
- **channels_last + AMP + TF32**: PyTorch enables TF32 for convolutions by default on Ampere; channels_last memory format is designed to pair with AMP to better feed Tensor Cores. Both are free wins to enable, though gains on a network this small (few channels, 9×9 spatial) are proportionally smaller than on ImageNet-scale ResNets — small-channel-count convolutions are documented to be more memory/launch-bound than compute-bound, which caps how much Tensor Core layout tricks alone can buy.
- **`multiprocessing` spawn overhead**: Windows has no `fork()`, so every worker process starts via `spawn` — a fresh interpreter plus pickling of everything sent to it — which is markedly slower to launch than Linux's copy-on-write `fork`. This penalizes Architecture A/C's process-per-game-worker model specifically at start-up/restart time, not steady-state throughput; keep long-lived worker pools rather than spawning per iteration.

## 3. Using two GPUs of different sizes (3090 + 3060)

There is no NVLink bridge between a 3090 and a 3060 (and consumer NVLink bridges are card-specific; a 3060 has no NVLink connector at all), so any communication between the two goes over PCIe. **Data-parallel training (DDP) across mismatched GPUs is a poor fit**: DDP synchronizes gradients every step and runs at the pace of the slowest replica, so pairing a 3090 with a ~2.5–3× slower 3060 wastes most of the 3090's throughput waiting at each all-reduce barrier — the standard multi-GPU guidance is to use identically-specced cards for DDP, and to reach for model/pipeline-sharding (FSDP) rather than DDP when memory, not compute-matching, is the constraint. Since the UTTT network is tiny (well under a GB), memory sharding is irrelevant here, so the natural pattern is not DDP at all but **role separation**, following directly from Section 2's finding that self-play is >90% of wall-clock:

- **RTX 3090 → self-play inference server(s).** Give the higher-throughput card to the workload that dominates total time. Its extra ~2.5–3× compute and larger batch headroom (24GB) matter most here.
- **RTX 3060 → training + evaluation/gating matches.** Gradient steps on a network this size are cheap and infrequent relative to self-play volume, so the weaker card is not a bottleneck; it can also host the periodic "new network vs. best network" evaluation matches (themselves just batched inference) without competing with self-play for the 3090.
- Alternative: run self-play workers on **both** GPUs independently (each hosting its own inference server for its own game pool, no cross-GPU communication) to add the 3060's throughput to the total, with training run in short bursts on whichever GPU is momentarily free. This adds ~30–40% more aggregate self-play throughput versus 3090-only, at the cost of more moving parts.

Either pattern avoids DDP's slowest-common-denominator problem entirely, since the two GPUs never need to agree on a gradient in lockstep.

## 4. Back-of-envelope plan for UTTT

Assumptions (stated explicitly, per the request):
- Raw NN throughput on the 3090 for a 6×64 net: **R = 200,000 evaluations/sec** (middle of the 150K–400K range derived in Section 2).
- MCTS simulations per move: **S = 100** (mid-point of the 64–200 range; Pgx used just 32 for Go 9×9, boardlaw used 64 for Hex, so 100 is a deliberately conservative middle value for UTTT's tactical, forcing-sequence character).
- Moves per game: **M = 50** (UTTT games can run up to 81 plies but commonly end earlier via a meta-board win).
- Tree reuse/caching ignored (worst case: every simulation is a fresh NN call — a real MCTS implementation with a transposition table would do somewhat better).

Arithmetic:
```
moves/sec  = R / S            = 200,000 / 100        = 2,000 moves/sec
games/sec  = moves/sec / M    = 2,000 / 50            = 40 games/sec
games/hour = games/sec × 3600 = 40 × 3600             = 144,000 games/hour
```
Sensitivity: at the low end of throughput (100K eval/sec) with heavier search (200 sims/move), games/hour drops to `100,000/200/50×3600 ≈ 36,000`. At the high end (400K eval/sec, 64 sims/move), it rises to `400,000/64/50×3600 ≈ 450,000`. So the plausible **range is roughly 35,000–450,000 self-play games/hour**, i.e., a UTTT self-play generator on this 3090 is very unlikely to be starved for data at any reasonable target game count — the reference-point table above shows strong small-game agents built from 50,000 (Othello, world-class-competitive) to ~1.3M games (Go 9×9, Pachi-competitive, derived as 52M frames ÷ ~40 moves/game for the Pgx baseline checkpoint) to tens of millions (Hex, provably-near-perfect). Even at the pessimistic 36,000 games/hour end, reaching:
- **50,000 games** (Othello/OLIVAW-strength anchor): **~1.4 hours**
- **~1.3M games** (Go-9×9/Pachi-strength anchor): **~36 hours (1.5 days)**
- **10M games** (approaching Hex-style near-solved play): **~11.5 days**

The realistic bottleneck for reaching *strong* (not provably perfect) UTTT play is therefore not self-play throughput but training-loop wall-clock overhead (Python orchestration, checkpoint I/O, evaluation-match gating, hyperparameter iteration) and engineering time to get Architecture B/C's vectorized self-play working correctly — the same lesson the `boardlaw` paper draws about the "takeoff" and "plateau" of its compute-vs-Elo curves: getting from random play to *decent* play is cheap and fast; the last few hundred Elo toward provably perfect play costs disproportionately more (roughly 7× more compute per additional board-size increment, or ~10× compute per +500 Elo in the linear regime). A pragmatic target for this machine is **low hundreds of thousands of self-play games over a few hours to at most one or two days**, which the arithmetic above shows is comfortably within budget if the self-play engine hits even the low end of the estimated throughput range — meaning the real project risk is implementation correctness and iteration speed, not raw GPU-hours.

## 5. Software recommendations for Windows without a compiler

- **Numba**: confirmed to work without any C/C++ compiler or even a system LLVM install — `llvmlite` (Numba's LLVM binding) ships LLVM statically linked into its wheel, so `pip install numba` is sufficient on its own. This makes Architecture C (Numba-JIT'd UTTT rules/legal-move generation + batched PyTorch inference) fully viable on this machine as-is.
- **Visual Studio Build Tools**: worth installing only if a genuine C++ extension (e.g., a hand-written bitboard MCTS engine, or to unlock `torch.compile`'s CPU backend and the unofficial `triton-windows` GPU path) becomes necessary later. For the Architecture B/C plans above, it is not a prerequisite — Numba and stock PyTorch cover the need. If installed regardless (cheap, ~a few GB), it also unblocks building any future Cython/pybind11 UTTT engine without reaching for WSL.
- **PyTorch CUDA wheel**: for an RTX 3090 (Ampere, compute capability 8.6), both `cu126` and `cu128` wheels are fully supported; `cu128` is the more future-proof current default (newer cuDNN, actively the baseline for newer ecosystem packages) and is safe on Windows for full cuDNN functionality — pick `cu128` unless a specific dependency pins `cu126`.
- **Pin versions**: lock `torch`, `numba`/`llvmlite`, and CUDA driver version together in a requirements file/lockfile from the start; Numba/llvmlite releases are sensitive to Python version compatibility, and PyTorch CUDA wheels are sensitive to driver version floors — an unpinned upgrade of either mid-project is a common source of silent slowdowns or crashes.
- **Monitoring**: TensorBoard (bundled with PyTorch via `torch.utils.tensorboard`, zero extra infra) or Weights & Biases (richer dashboards, used by several of the small AlphaZero repos surveyed above, e.g. [zhihanyang2022/alpha-zero](https://github.com/zhihanyang2022/alpha-zero)) for loss curves, self-play throughput, and Elo-over-time plots.
- **Rating tracking**: BayesElo (used by both the original AlphaZero paper and the [Pgx paper](https://arxiv.org/abs/2303.17503)) or TrueSkill for tracking generation-over-generation strength via periodic gating matches — both are standard, well-documented choices; BayesElo specifically models draw rate and first-move advantage, relevant since UTTT is not symmetric move-for-move.
- **Replay buffer storage**: NumPy structured arrays (or a plain memory-mapped `.npy`/`.dat` file of fixed-size records: board planes + policy target + value target) are the simplest durable format for a buffer of millions of small UTTT positions and avoid pickling overhead; with 128GB RAM, buffers of several million positions can likely stay fully in memory, sidestepping disk I/O entirely for a game this small.
- **WSL2 for JAX/pgx/mctx GPU**: **yes**, installing WSL2 would unlock the JAX ecosystem (Pgx's own environments, DeepMind's `mctx` for batched MCTS) with GPU passthrough, since JAX's Windows-native GPU support is far behind its Linux support. Trade-offs: WSL2 GPU compute is reported at roughly 5–15% overhead versus native Linux for typical workloads (with reports of up to ~33% for some heavy workloads), file I/O across the Windows/WSL boundary is a known extra penalty if datasets sit on an NTFS-mounted drive rather than the WSL ext4 filesystem, and it adds a second environment (drivers, CUDA toolkit versions, Python env) to maintain in parallel with the native Windows PyTorch setup. Given this project's existing investment in a PyTorch CUDA 12.6 setup, the pragmatic recommendation is to build Architecture B/C directly in PyTorch on native Windows first, and treat a WSL2 + JAX/pgx/mctx port as a fallback only if PyTorch self-play throughput proves to be a genuine bottleneck against the Section 4 estimates.

## Recommended architecture for this machine

**Architecture C (Numba-JIT'd UTTT rules + batched-tensor MCTS + PyTorch inference server), with role-separated dual GPUs**: run the self-play loop as a pool of long-lived worker processes (avoiding per-iteration `spawn` cost) whose game logic and move-legality checks are Numba-compiled, feeding leaf-evaluation requests into a batched inference server pinned to the RTX 3090; use CUDA graphs (not `torch.compile`, which lacks solid Windows GPU support) to shrink per-batch launch overhead; enable TF32 and channels_last by default (cheap, no downside for this net size); run training minibatches and network-vs-network gating matches on the RTX 3060, avoiding DDP entirely since the two cards never need to synchronize gradients. If early profiling shows the Numba/Python self-play loop falling well short of the ~150K–400K eval/sec ceiling estimated in Section 2, migrate the hot path toward a more fully tensorized Architecture B (batched game-state tensors + `vmap`-style MCTS) before considering a WSL2/JAX rewrite.

## Key takeaways

1. Self-play, not training, consumes >90% of AlphaZero wall-clock time on small games — confirmed directly in the Pgx paper's own Go 9×9 experiment.
2. The best concrete anchor for UTTT is Pgx's Go 9×9 run: a 6×128 ResNet, 32 sims/move, reached a Pachi-competitive baseline in 8.6 GPU-hours on a single A100 (~3,400 positions/sec end-to-end, ~1.1×10⁵ raw NN evals/sec).
3. Scaling that anchor down to a 6×64 net on an RTX 3090 gives an estimated **150,000–400,000 raw NN evaluations/sec**, which is an extrapolation, not a measured number — validate with a local microbenchmark early.
4. Small-game reference points span three orders of magnitude in self-play games needed: ~50,000 for competitive-with-strong-humans (Othello/OLIVAW) up to tens of millions for provably-near-perfect play (Hex 9×9 boardlaw).
5. No published, benchmarked UTTT-specific AlphaZero compute numbers exist; UTTT must be positioned by analogy to Go 9×9/Hex 9×9 (same board footprint) pending this project's own measurements.
6. Fully vectorized self-play (Architecture B, pgx/mctx-style, or Architecture C's Numba-hybrid) is 1–2 orders of magnitude faster than CPU-tree-search-per-game (Architecture A) for a game this small and cheap to simulate.
7. `torch.compile` GPU support does not work out-of-the-box on Windows (Triton dependency); CUDA graphs are the practical, compiler-free alternative for cutting kernel-launch overhead.
8. Numba requires no C/C++ compiler on Windows (LLVM is statically bundled in `llvmlite`'s wheel) — Visual Studio Build Tools are optional, not required, for the recommended architecture.
9. DDP across a 3090+3060 is a bad fit (no NVLink, ~2.5–3× speed mismatch forces every step to the slower card's pace); role-separating self-play (3090) from training/eval (3060) sidesteps the problem entirely.
10. Back-of-envelope arithmetic (200K eval/sec, 100 sims/move, 50 moves/game) yields ~144,000 self-play games/hour, meaning even a multi-million-game training target is plausibly reachable in **hours to a few days**, not weeks — the dominant project risk is implementation/engineering time, not raw compute.
